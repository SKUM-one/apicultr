## Identity

- Product name: **apicultr** (lowercase, no trailing `e`)
- Pronunciation: "API Cult-er." Dual etymology stacks deliberately:
  - **apiculture** (the ancient craft of beekeeping; keeper of swarms)
  - **API + cult + -er** (the keeper of the API cult)
- Tagline: **apicultr keeps your hive. You are the king.**
- Binaries shipped: `apicultr` (install / update / manage the product itself) and `hive` (the daily-use CLI for commanding your hive). See "Two binaries" below.
- One-liner: a cross-platform multi-process agent swarm orchestrator. Spawns N independent Claude Code workers, each in its own terminal window (native Mac primary, tmux fallback), arranged in any hierarchy from a flat hub to a deeply nested org. Customer brings their own Claude Code.
- What it is not: a hosted service, an LLM, an agent itself, a chat-style assistant. apicultr is the runtime + CLI that hosts and dispatches to a literal team of Claude Code processes.

## Brand positioning: the king is outside the hive

The bee/hive metaphor is older than software. Multiple agent products (Ruflo's hive-mind, etc.) use it. apicultr's distinctive framing is *where the sovereign sits*.

- In other agent products with hive vocabulary, a **Queen** lives inside the software and coordinates worker agents internally. The orchestration is software-internal.
- In apicultr, there is no Queen. **The human customer is the King.** apicultr is the keeper. The hive serves the King. Orchestration is human-led, with the hive as a literal team of independent workers the King can see, direct, and override.

This isn't a marketing affectation. It maps to the actual architectural difference: apicultr's workers are real Claude Code processes the customer can talk to directly, not logical agents routed by an internal supervisor. The "owns the hive" framing in copy matches the "sees and controls every worker" reality in product.

Inside the hive, the orchestration roles are functional, not regal:
- **Chief** (top), **Lead-<domain>** (mid), **<domain>-NNN** (workers).
- No Queen. The Queen title belongs to the customer.

## Two binaries: `apicultr` and `hive`

Hard split between the product and the user's hive:

- **`apicultr`** is the *product* CLI. You touch it rarely: install, update, version check, uninstall, account/licence management when those exist. Lightweight, mostly invoked once at setup and then dormant. Pattern: like `rustup` for Rust.
- **`hive`** is the *daily* CLI. Every action a customer takes against their own hive goes through `hive <verb>`: bring it up, dispatch a brief, attach, status, tear down. The user is commanding their hive, not commanding apicultr.

A `hive` binary was chosen over `swarm` to avoid conflict with the legacy `swarm-shell.zsh` namespace (`swarm-dispatch`, `swarm-arrange`, `launch-swarm`) that the existing Atras runtime ships. "Agent swarm" survives as the industry-category positioning language; "hive" is the user-owned noun inside the product.

## Why apicultr exists (competitive context)

The agent-orchestration space in 2026 has three established product shapes:

1. **Anthropic Claude Code Agent Teams** (official, v2.1.32+, experimental). Spawns parallel Claude Code processes coordinated by a lead. **Flat topology only**: no nested teams, no Foreman → Lead → Worker structure. No split panes in Ghostty, Windows Terminal, or VS Code (tmux or iTerm2 only). Worktree handling is manual.
2. **Ruflo** (40k+ stars, ruvnet/ruflo). Single Claude Code session augmented with MCP-routed logical agents in a hive-mind architecture. Sophisticated but a **different product category**: it makes one session smarter about routing, rather than spawning a visible team of independent processes. Buyer sees one chat-style session, not a team of workers.
3. **apicultr** (this spec). N independent Claude Code processes, each in its own visible terminal window, dispatched via tmux or native Mac windows, organised hierarchically. The "visible team" model that the Atras swarm has validated in production for a year.

apicultr is differentiated on five axes Ruflo and Agent Teams do not cover together:

| Axis | apicultr | Ruflo | Agent Teams |
|---|---|---|---|
| Process model | N independent Claude Code processes | 1 session + MCP routing | N processes, flat |
| Visible team | Every worker has its own window | No (chat UI) | Yes, but flat |
| Hierarchical depth | Unbounded (Chief / Lead / Worker, with sub-hives) | Flat at runtime (logical agents are routed, not nested) | Explicitly forbidden |
| Native Mac UX | First-class (floating-overlay layout) | None | None |
| Context budget | N × 200k (per-worker context isolation) | 1 × 200k | N × 200k, flat |
| Human-direct dispatch | First-class (King → any worker) | Via orchestrator | Yes |
| Customer brand role | King outside the hive | None (queen inside) | None |

The Atras swarm is the existing real-world test of this approach. apicultr is the productized version. The dev-swarm template, sized to scale a small studio's dev capacity into a 30 to 50 worker hive, is the v1 SKU.

## Core primitives

- **hive**: a coordinated set of workers for one project, with a declared topology. Cross-platform: one tmux session under the tmux backend, one set of Mac Terminal.app windows under the native backend.
- **persona**: a single worker. One Claude Code instance with a specified model, identity doc, workspace, and an address inside the hive's role hierarchy.
- **role**: a persona's position in the hive. Roles include `chief`, `lead-<domain>`, `<domain>` (worker). Roles encode permitted dispatch direction.
- **sub-hive**: a hive composed inside another hive. Its own `hive.toml`, its own internal hierarchy, integrated into the parent via reference. Enables deep nesting and multi-product orgs without monolithic configs.
- **brief**: a unit of work dispatched to a persona. Markdown file or inline string.
- **report**: a persona's response, written to a conventional file path.
- **orchestrator-by-role**: any persona may dispatch to personas below it in the hierarchy. Soft enforcement via persona identity doc, hard enforcement deferred to v1.x.

## Window backends

apicultr v1 ships **two** window backends. The customer's `hive.toml` declares which one to use; doctor auto-detects what the system supports.

### Native Mac backend (primary, marquee UX)

- **One native Mac Terminal.app window per persona.** Arranged in a grid sized to the user's screen.
- **The Chief's terminal AND the user's terminal float as semi-transparent overlays.** 50% opacity background, blur, opacity rises to ~95% on focus.
- Drives the visible "you can see your whole team working" experience the Atras swarm built its workflow around.
- Implementation: osascript for window control + AppleScript for grid layout + Terminal.app per-window opacity (already supported natively).
- Supported terminals: Terminal.app first-class. iTerm2 secondary. Ghostty does not support per-window opacity sufficiently and is not supported by this backend in v1.
- The grid size is **computed from the active display's resolution at `hive up` time, not hardcoded**. Algorithm: query the primary display's logical points via `system_profiler` or AppleScript display bounds; subtract menu bar + dock; divide by `target_window_size_px` from `hive.toml`; produce a row-column grid that fits within the workable area; arrange persona windows top-to-bottom, left-to-right. Multi-display: workers tile on the primary display unless `hive.toml` declares a target display ID. A 14" MBP fits ~15 worker tiles at default sizing; a 6K display fits significantly more. The existing v12.1 osascript hardcoded `SWARM_WIN_W=411, SWARM_COLS=5` for a specific 16" MBP screen is **not** the model to copy; apicultr must compute, not assume.

### tmux backend (cross-platform fallback)

- **One tmux session per hive, one tmux window per persona.**
- Dispatch via `tmux load-buffer` + `tmux paste-buffer` + `send-keys Enter`.
- Native on macOS and Linux; runs under WSL2 on Windows.
- No floating-overlay UX. The customer attaches with `hive attach` and uses tmux's native window navigation.
- This is the "engineering-respectable fallback" for users who can't or won't use the native Mac backend.

The dispatch primitive is the same across backends. The persona identity docs, hive.toml schema, brief/report convention are all backend-agnostic. Only the display and window lifecycle differ.

## Naming convention

Every persona has a canonical **address** and an optional **codename**.

### Address (canonical, machine-readable, infinite)

Format: **`<role>-<3-digit-padded-index>`**

Examples:
- `chief-001` (always one chief per hive; suffix kept for format consistency)
- `lead-architecture-001`, `lead-frontend-001`, `lead-backend-001`, `lead-design-001`, `lead-qa-001`
- `frontend-001`, `frontend-007`, `frontend-042`, `frontend-123`
- `backend-001`, `qa-001`, `design-001`, `architecture-001`

Properties:
- **Infinite by construction.** Padding is 3 digits; past 999 it grows to 4 digits naturally.
- **Self-describing.** Role and position in one token.
- **Sorts cleanly.** Padded numbers preserve numeric order under alphabetic sort.
- **Hyphen-separated.** CLI-friendly, no shell escaping.
- **Stable.** Indexes never recycle; gaps are fine.

Roles are template-defined, not runtime-hardcoded. A non-dev-swarm template could define its own roles.

### Codename (optional, conversational)

Customers can humanise their hive:

```toml
[[personas]]
address = "frontend-001"
codename = "Mira"
```

`hive dispatch` accepts either: `hive dispatch frontend-001 < brief.md` or `hive dispatch mira < brief.md`. Address is canonical; codename is conversational. Default: no codename. Address is the only name. No curated codename pools shipped with v1.

## Default model selection by role

The v1 dev-swarm template ships with these per-role defaults; customer overrides per-persona:

- **Chief**: `claude-opus-4-7`
- **Lead-<domain>** (all): `claude-opus-4-7`
- **Workers** (all): `claude-opus-4-6`

Rationale: orchestration roles benefit from the strongest model (judgement, brief-decomposition, cross-domain synthesis); workers can run on the previous-tier model at materially lower per-token cost without quality loss for execution work.

## Runtime architecture

- One hive per project: a coordinated set of N personas.
- Each persona = one Claude Code process. Started with `claude --model <model> --dangerously-skip-permissions` in the persona's workspace dir.
- Dispatch primitive: `hive dispatch <persona>` reads brief content from stdin or `--brief <file>`, writes to `.hive/briefs/<persona>/<date>-<slug>.md`, delivers into the persona's Claude Code session via the active backend (native Mac windows or tmux).
- **Dispatch auto-sequences internally.** Rapid back-to-back `hive dispatch` calls do NOT clobber each other. The runtime holds a per-hive dispatch lock (filesystem flock on a `.hive/dispatch.lock` file) so concurrent invocations queue rather than racing on the clipboard / paste-buffer. The legacy `swarm-shell.zsh` required a manual `sleep 1.5` discipline between calls; apicultr makes the discipline unnecessary by enforcing serial dispatch under the hood.
- **Persona-to-persona dispatch is a first-class primitive.** Any persona's Claude Code session has `hive` on PATH. A Lead may shell out: `hive dispatch frontend-007 < brief.md`. Mechanism is identical to human-initiated dispatch, including the auto-sequencing lock. Authorisation is soft (encoded in dispatcher's persona doc) in v1; hard authorisation rules land in v1.x.
- Sub-hive composition: a parent hive's `hive.toml` references child hive directories. `hive up` recurses into each sub-hive and brings them up with namespaced addresses (`<sub-hive>:<address>`).

## CLI surface

### `hive` (daily use)

```
hive init <name> [--template <template>] [--path <path>] [--backend native|tmux|auto]
  Scaffold a new hive at <path>/<name> (default <path> = cwd).
  --template copies persona docs + hive.toml from the named template.
  --backend defaults to auto (native on macOS, tmux elsewhere).

hive up [<name>] [--detach]
  Start the hive: spawn each persona's Claude Code in its window
  (native Mac windows or tmux windows per backend).
  Recursively brings up sub-hives. --detach (default) returns immediately.

hive dispatch <persona> [--hive <name>] [--brief <file>]
  Read brief from stdin (default) or --brief <file>, send to <persona>.
  <persona> may be either an address (frontend-007) or a codename (mira).
  Echoes the brief ID and path.

hive attach [<persona>] [--hive <name>]
  Bring the hive to focus. Native backend: arranges + raises the windows.
  Tmux backend: tmux attach -t <session>. Optional <persona> focuses one.

hive status [<name>] [--json] [--tree]
  List active hives with per-persona status.
  --tree renders the topology hierarchy.
  Per-persona health signals: running (process alive + window present),
  ready (claude prompt visible), busy (mid-turn, last paste < N seconds),
  blocked (plan-mode approval prompt detected), stalled (no output for N
  minutes), dead (process exited or window closed).

hive down [<name>] [--force]
  Tear down the hive. Native backend: close all persona windows.
  Tmux backend: kill the tmux session.
  --force tears down even with active dispatches.

hive route <persona> [--hive <name>]
  Print where <persona> sits in the hierarchy and what they can dispatch to.

hive persona <subcommand>
  list                    list personas in the current hive
  add <role>              add a new persona at the next index in <role>
  remove <persona>        remove a persona (kills its window if up)
  restart <persona>       restart a single persona's claude process

hive template <subcommand>
  list                    list available templates
  show <name>             print template manifest

hive backend
  Print which backend is in use and what alternatives the system supports.

hive doctor
  Check tmux >= 1.9, claude installed and on PATH, paths writable,
  Mac native backend prerequisites (Terminal.app present + osascript working),
  no PATH conflicts with swarm-shell.zsh. Pre-flight for any hive.
```

Common flags: `--config <path>`, `--verbose`/`-v`, `--quiet`/`-q`.

### `apicultr` (rare use; manage the product itself)

```
apicultr version
  Print apicultr + hive CLI versions, tmux version, claude version, Terminal.app version on macOS.

apicultr update [--channel <stable|beta>]
  Self-update apicultr + hive binaries from the release channel.

apicultr uninstall
  Remove apicultr + hive binaries. Leaves user hives untouched.

apicultr account <subcommand>     # placeholder for when licensing lands
  status                  show licence / subscription state
  activate <key>          activate an apicultr key
```

A customer types `apicultr` maybe once a month. They type `hive` every working day.

## hive.toml schema

```toml
[hive]
name = "skum-studio"
description = "SKUM dev/design hive: Atras + Kant.codes + client work"
workspace_root = "."

[topology]
shape = "hierarchical"      # "hub-spoke" | "hierarchical" (v1)
                            # "pipeline" | "event-driven" (v1.x, reserved)
human_dispatch = "any"      # "any" | "chief-only" | "named"

[runtime]
backend = "native"          # "native" | "tmux" | "auto"
default_model = "claude-opus-4-7"
acknowledged_dangerous = true        # required for hive up to proceed

[runtime.native]                     # native-backend-only config
target_window_size_px = [480, 320]   # width, height per worker window
overlay_opacity = 0.5                # Chief + user terminal background opacity
overlay_focus_opacity = 0.95         # opacity when overlay terminal is focused
use_blur = true                      # enable Mac vibrancy blur behind overlays

[[personas]]
address = "chief-001"
role = "chief"
identity_doc = "personas/chief.md"
workspace = "./chief-001"
model = "claude-opus-4-7"
manages = ["lead-architecture-001", "lead-frontend-001", "lead-backend-001",
           "lead-design-001", "lead-qa-001"]

[[personas]]
address = "lead-frontend-001"
role = "lead-frontend"
identity_doc = "personas/lead-frontend.md"
manages = ["frontend-001", "frontend-002", "frontend-003", "frontend-004", "frontend-005"]
reports_to = "chief-001"

[[personas]]
address = "frontend-001"
role = "frontend"
identity_doc = "personas/worker-frontend.md"
reports_to = "lead-frontend-001"
# manages absent: this is a leaf worker

[[sub_hives]]
name = "kant-codes-hive"
path = "./kant-codes"                # relative; points at a dir with its own hive.toml
attach_under = "chief-001"           # this sub-hive reports to chief-001 in the parent

[briefs]
path_template = ".hive/briefs/{persona}/{date}-{slug}.md"

[reports]
path_template = ".hive/reports/{persona}/{date}-{checkpoint}.md"
```

`manages` is the authoritative edge list of the hierarchy. The runtime uses it to:
- Render `hive status --tree`
- Resolve `hive route <persona>`
- Generate soft-policy text injected into each persona's identity doc at `hive up` time ("you may dispatch to: <managed list>")

## Persona doc format

```markdown
---
address: lead-frontend-001
role: lead-frontend
codename: Mira                       # optional
model_preference: claude-opus-4-7
tools_needed:
  - mcp-supabase
  - mcp-figma
manages:
  - frontend-001
  - frontend-002
  - frontend-003
  - frontend-004
  - frontend-005
reports_to: chief-001
---

# Lead, Frontend

You are the Frontend Lead of this hive. Your address is lead-frontend-001.
You report to the Chief (chief-001) and the King (the human running this hive).

[Full identity: domain expertise, how you break briefs into worker-sized tasks,
how you grade incoming PRs from your workers, when you escalate to the Chief,
how you handle cross-domain dependencies with peer Leads, voice and style.]
```

The persona doc is loaded by `hive up` and pre-pended into the persona's initial Claude Code session as a system context message, alongside an auto-generated "Hierarchy" block (managed personas, reports_to relationship, King's name/role for context) and a "Dispatch primitive" block describing how to use `hive dispatch` when delegating.

## Language and runtime

- **TypeScript on Bun.** Single-binary distribution via `bun build --compile`. Cross-platform from day one. Matches SKUM's existing TS/Astro/React stack so SKUM engineers can contribute without context-switching. When the Tier 3 web dashboard lands later, runtime and dashboard share a language and type system.
- Native Mac backend uses osascript via `child_process.spawn` for window control. AppleScript snippets shipped as resources in the binary bundle.
- Bun is required for the build pipeline. Node fallback is possible (for ARM Linux distribution where Bun is less proven) but not v1 scope.

## Cross-platform notes

- **macOS** (arm64, x64): native Mac backend (default) OR tmux backend (opt-in). Both fully supported.
- **Linux** (arm64, x64): tmux backend only. Native backend gracefully refuses with a clear message pointing to tmux.
- **Windows**: WSL2 only. Tmux backend only. Native Mac backend obviously unavailable.
- Path handling: POSIX-only internally. Conversion at the WSL boundary.

## Out of scope for v1

- Web dashboard / hosted service (Tier 3)
- Hard authorisation enforcement on persona-to-persona dispatch (soft, via identity docs, in v1)
- Pipeline and event-driven topologies (reserved strings only)
- Multi-machine / distributed hives (one host)
- Authentication / multi-user (single-user CLI)
- Persistent worker state separate from Claude Code's own session state (the tmux window or native Terminal.app window is the state)
- Native Windows shell (PowerShell host)
- Centralised MCP server pool (each persona's Claude Code manages its own MCP connections in v1)
- A "hive builder" GUI for assembling personas
- Ghostty support for the native backend (Terminal.app and iTerm2 only in v1)
- Lead-gen template content (v1.1 SKU)

## Open questions and risks

1. **Large brief sizes.** `tmux load-buffer` and AppleScript paste are fine for kilobytes but very large briefs could hit practical limits. Mitigation: write to a file and have the persona read the path. Implement chunked dispatch only if real briefs exceed N.
2. **Claude Code crash recovery.** If a persona's claude process dies mid-dispatch, the dispatch errors out. `hive persona restart` covers manual recovery.
3. **MCP server lifecycle.** Each persona's Claude Code manages its own MCP. Duplicated processes per persona at 30 to 50 personas could be heavy. Measure during dogfood.
4. **Bun on ARM Linux.** Less well-trodden than x64. Fallback path may need Node.
5. **First-run permissions.** `--dangerously-skip-permissions` is used by all personas. `hive init` requires explicit `acknowledged_dangerous` in hive.toml before `hive up` will proceed.
6. **Brief ID convention.** v1: ID is the brief's filesystem path. v1.1 may add a content-hash short ID.
7. **Tmux pre-1.9 syntax.** `hive doctor` enforces tmux >= 1.9.
8. **Sub-hive name collisions.** Dispatch parser handles namespace prefix.
9. **Soft hierarchy enforcement could be ignored.** v1 accepts this risk; the dispatcher is itself an LLM and the identity doc is the policy contract. Hard enforcement is v1.x.
10. **AppleScript window arrangement under stage manager / hidden spaces.** Mac users in mission-control-heavy workflows may have window-arrangement quirks. Document and degrade gracefully.
11. **Focus-steal guard parity with legacy.** The legacy `swarm-shell.zsh` dispatcher checks `frontmost of process "Terminal"` immediately before paste and aborts with clipboard preserved if focus has left Terminal. apicultr's native backend MUST implement the same guard: a 0.5s settle, then a frontmost check, abort with clear error if not. Two edges remain even with the guard: (a) the guard does not distinguish target persona's window from other Terminal windows (Cmd-Tabbing to a sibling persona during the settle window means paste lands in the wrong window); (b) microsecond race between check and paste. Both are acceptable v1 risks; (a) can be tightened later by checking window UID, not just app frontmost.
12. **Grid math from screen, never hardcoded.** Hardcoded grid dimensions (the legacy v12.1 pattern) break on any display other than the original 16" MBP. apicultr computes grid layout from the active display's resolution at `hive up` time.
